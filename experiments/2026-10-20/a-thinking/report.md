# 一家 200 人的研发企业准备在内网私有化部署代码与知识库问答助手，硬件预算 200 万以内，要求支持 50 人并发：直接买华为昇腾 910B 一体机跑满血 DeepSeek-V4.1-Flash-1017（552B），还是用 4 张 RTX PRO 6000（96GB×4）工作站跑 GLM-5.3-Flash（320B）？请对比两套方案的算子适配坑点、吞吐延迟与运维成本。

## P1 · 背景

本报告针对一家约 200 人的研发企业的内网私有化大模型选型需求展开。该企业计划部署两套应用：面向研发人员的代码助手（以多轮 Agent 工具调用为主，前缀缓存命中率高）和面向内部文档的知识库问答（RAG 召回片段拼入提示词）。硬件预算上限为 200 万元人民币，名义并发要求为 50 人；经澄清，50 人指“日常在线办公人数”，峰值同时运行的请求数约为 10 至 15 路，因此容量规划的真实口径应是 10 至 15 路并发生成，而非 50 路持续生成。服务等级要求为：首 token 延迟（TTFT）不超过 5 秒，单路生成速度不低于 25 token/s。单次会话上下文平均 32K 词元、峰值 128K 词元。组织侧的关键约束是团队仅有一名兼职运维人员，且没有强制使用国产算力卡的信创要求，明确“优先看好不好部署维护”。上述业务口径、并发定义、SLA 与上下文规模均来自需求方对澄清问题的回答，本报告将其作为既定输入处理。

候选方案有两套。方案 A 是直接采购华为昇腾 910B 一体机，运行需求方所称的“满血”DeepSeek-V4.1-Flash-1017（552B 主干 + 196B Engram，预填充阶段激活 8B、解码阶段激活 16B，原生 FP8+FP4 混合精度约 510GB，采用 CSA2 压缩 KV，1M 上下文）。方案 B 是采购一台搭载 4 张 NVIDIA RTX PRO 6000（96GB×4）的工作站，运行 GLM-5.3-Flash（320B 总参、18B 激活，34 层 KDA 线性注意力 + 11 层 DSA 稀疏 MLA，1M 上下文，支持 FP8/INT4）。需要在一开始就明确说明一个重要的证据边界：这两个模型的名称、参数结构、激活参数量、精度格式与显存占用数字，全部来自需求方的回答，本次检索所获得的六份材料中没有任何一份提及或验证过这两个型号；因此本报告中凡涉及这两个模型规格之处，均属于“委托方提供的输入”，而非可核验的公开事实，据此推导出的显存、吞吐与延迟只能作为区间估算或方向性判断，不能作为采购承诺的依据。这一证据缺口本身构成选型风险的一部分，将在“挑战”一节中单独讨论。

之所以需要一份专门报告，是因为这两套方案代表的是两条差异相当大的技术栈，而非仅仅是两种显卡。方案 A 的软件形态是 CANN、torch_npu、vLLM-Ascend 插件构成的国产 NPU 栈，其算子覆盖、图模式约束、自定义算子环境依赖都有公开记录的“坑点”；方案 B 的软件形态是 NVIDIA Blackwell 架构中属于 SM120 的那一支（RTX PRO 6000 系列），它与数据中心 SM100 系列（B100/B200/GB200）的预编译 FP8 算子包并不通用，需要从源码编译或等待上游适配 [S6]。与此同时，两个被选模型都是高度稀疏的结构（激活参数分别为 8B/16B 与 18B），这意味着单路解码速度主要由激活权重的读取量与 KV 读取量决定，而总参数量主要影响的是显存容量与采购成本，这一区分是后文所有吞吐判断的基础。

## P2 · 现状

一、昇腾 910B 侧的软件栈现状。vLLM Ascend 是 vLLM 的硬件插件，其官方 FAQ 给出的支持矩阵是：目前支持 Atlas A2 系列（Ascend-cann-kernels-910b）、Atlas A3 系列以及 Atlas 300I 系列（310p），覆盖 Atlas 800T/900 A2、Atlas 800I A2、Atlas 800T/900 A3、Atlas 800I A3，并实验性支持 Atlas 300I Duo；Atlas 200I A2 与“Ascend 910/910 Pro B”被列为不支持且无计划 [S4]。这一点对采购环节有直接影响：910B（对应 Atlas A2 内核包）在支持范围内，但 SKU 命名相近的型号并不必然同样受支持，一体机合同中的具体卡型必须与 vLLM-Ascend 的支持矩阵逐条核对。功能面上，该插件已支持以 Mooncake 为后端的 Prefill-Decode 分离，以及 w8a8、w4a8、w4a4 量化；测试体系覆盖功能（原生 vLLM 单测、插件单测、基础功能与热门模型可用性 E2E）、性能（基准工具，并规划为每个 PR 提供性能站点）、精度（正在纳入 CI）以及夜间全量测试 [S4]。运维排障方面，FAQ 记录了“Failed to infer device type”或 libatb.so 相关报错通常源于 NPU 环境未正确 source（需依次 source ATB 与 ascend-toolkit 的 set_env.sh，再确认 npu-smi info）[S4]；OOM 的三条常规手段是限制 max-model-len、调整 gpu-memory-utilization（默认 0.9）、以及设置 PYTORCH_NPU_ALLOC_CONF=expandable_segments:True 降低碎片 [S4]。

二、昇腾侧具体算子适配经验。Xinference 的故障记录提供了一个典型样本：原生 vLLM 能正常启动并对话，但同一个模型通过 Xinference 启动时报“循环状态 dtype 错误”；根因是 Xinference 拉起的进程没有继承原生 vLLM 环境中存在的自定义算子路径，导致缺失自定义 GDN/Mamba 算子环境后回退到 CANN 内置算子，而内置算子在该场景下拒绝了模型的 float32 状态。该记录的处置建议是同时检查 ASCEND_CUSTOM_OPP_PATH 与 LD_LIBRARY_PATH 中的自定义 op_api/lib 条目，在同一个 shell 中 source vLLM-Ascend 的自定义环境后再启动 Xinference，并设置 VLLM_DISABLE_SHARED_EXPERTS_STREAM=1，最后在版本记录中一并写明 CANN、torch-npu、vLLM 与 vLLM-Ascend 的版本号和镜像 tag [S1]。这个案例的价值在于它揭示了昇腾侧的“坑”往往不是模型本身，而是环境继承与算子分发链路：同一套权重，换一个启动壳就可能从可用变为不可用，且报错信息指向精度而非环境。

另有一篇中文部署手记声称在两张单卡 32GB HBM 的 910B 服务器上部署了一个 236B 稠密模型，并记录了相当详细的过程与压测数据：原生 vLLM 镜像因硬编码 CUDA Runtime 调用而在昇腾上失败，需将 _init_cuda 替换为 _init_npu、以自写的 ascend_flash_attn_varlen 对接 aclnnFlashAttentionVarLenFwd 算子替代 flash_attn_varlen_func、并将 KV cache 分配切换到 torch.npu.empty；作者强调必须用 BF16 而非 FP16（权重本身为 bfloat16，FP16 会导致 swiglu 激活在 65504 以上溢出，并称 16K 上下文下 FP16 与 BF16 的 top-k 采样差异超过 37%）；服务层放弃 vLLM 自带 openai_api_server，改用 FastAPI 加 8 线程池与显式 ACL stream，声称使 P99 延迟标准差从 ±420ms 降至 ±83ms、CPU 占用从 98% 降至 41%；参数上 block_size 由 16 提到 32（称显存下降 12.7%）、gpu-memory-utilization 0.85、max-num-batched-tokens 4096、max-num-seqs 256、max_model_len 32768，并用预热脚本把首请求延迟从 12.3 秒降到 1.7 秒；压测声称稳定 QPS 142±3.2、P50 0.87 秒、P99 1.78 秒 [S2]。必须对该材料的可用性作出明确限定：它是单一站点的自述，未披露测试脚本、原始日志与可复现路径，且其声称的 236B 模型、4.4GB 权重、单卡 32GB 上 24.2GB KV cache 等数字彼此难以自洽，模型名称也与本报告的候选型号无关 [S2]。因此本报告只把它当作“昇腾侧会遇到哪些类别的问题”的定性参考，不采用其任何性能数字作为容量设计输入。

三、昇腾侧迁移方法论与精度校验现状。另一份面向工程师的迁移教程把工作拆成四块：对齐 CANN、驱动/固件、Python、PyTorch 与 torch_npu 的版本链；替换模型与设备处理（.cuda()/device='cuda' 改为 .npu()/device='npu'，并指出 device_map='auto' 在 NPU 上支持不完整）；适配不支持的算子；最后做精度与性能验证。它给出的示例版本组合是 CANN 8.0.RC1 配约 23.0.RC1 驱动、PyTorch 2.1.0 配 torch_npu 2.1.0.post8，建议权重在 CPU 上重新保存为 safetensors 以去除设备元数据，可用 transfer_to_npu 做快速算子映射但生产环境需逐个确认，分布式使用 HCCL [S5]。精度验收上，该文提出以 NPU 与 GPU/CPU 或外部 API 比对，最大 FP16 logit 差异在 1e-2 量级属正常，超过 1e-1 则应回查算子；同时给出单卡 910B 跑 7B FP16 约 20–40 token/s 的非正式经验值，以及 910B 卡存在 32GB 与 64GB 两种显存规格的说法 [S5]。这些数字同样是作者示例性陈述而非独立基准，但“版本链对齐 + 逐算子精度校验”的方法论与前述故障记录互相印证。

四、RTX PRO 6000 侧的可核验现状。一份双卡实测（2× RTX PRO 6000 Blackwell Max-Q Workstation Edition，单卡 96GB，300W 功耗墙，无 NVLink，跨卡走 PCIe，Threadripper 9960X、122GB 内存、驱动 595.91.07/CUDA 13.2、vLLM 0.29.0 与 ollama，测量日期 2026-09-10）给出了一组可用的锚点数据：对 gpt-oss-120b（MXFP4，MoE 总参 116.8B、每 token 约 5B 激活），单卡单流解码在 vLLM 中为 185 token/s（TPOT 5.3ms），ollama 中为 185.6 token/s，作者将其归因于解码受内存带宽约束、GPU 功耗远低于 300W 上限；单卡批量推理在 16 并发时升至 894 token/s、64 并发时 1786 token/s，而单请求解码速度相应降至约 58 与 29 token/s，中位 TTFT 升至 467ms 与 945ms；64 并发时 GPU0 触及 300W 峰值 [S3]。同一台机器的张量并行没有跑通：NCCL 在不关闭 P2P 时初始化挂起，设置 NCCL_P2P_DISABLE=1 后 FlashInfer 注意力核的预热又不可行（GPU 利用率 100% 但功耗仅 97W，持续十余分钟）；作者将其界定为 vLLM 0.29、gpt-oss MXFP4、Blackwell 与关闭 P2P 组合下的软件边界问题，而非硬件不具备多卡集合通信能力，因为 DDP 训练在同一台机器上跑通了（Qwen2.5-7B 全参微调单卡 3243 token/s、双卡 6010 token/s，扩展效率 92.7%，但需 NCCL_P2P_DISABLE=1）[S3]。ollama 的层切分（点对点中间拷贝而非 NCCL 集合通信）可以工作，且该文指出 MoE/稀疏激活对速度的影响大于总参数量 [S3]。需注意该文作者是销售含同款 GPU 工作站的系统集成商，存在商业利益，且自述文章非受托或赞助 [S3]。

五、Blackwell SM120 的软件生态现状与可用参考实现。另一份 8× RTX PRO 6000（96GB GDDR7、SM120、600W）工作站的 SGLang 部署实录提供了更接近本案例的工程量：服务对象是一个 27B 的 FP8 混合线性注意力模型（64 层 = 16 组 [3×(GDN→FFN) + 1×(GQA→FFN)]，即 48 层 GDN 线性注意力与 16 层 GQA，隐藏维 5120、FFN 17408，FP8 e4m3 blockwise [128,128] 动态量化，原生 262144 上下文可扩至 1M）。其性能结论是：单流解码从无投机采样的 46.6 token/s 提升到 DFlash2 + TP2 的 251.6 token/s（5.4×），C16 聚合吞吐 3524 token/s，2K 提示的 TTFT 约 60–62ms（归因于 48 层线性注意力的 O(n) 预填充）；C1/C4/C16 矩阵为基线 46/176/632、DSpark TP1 110/735/1832、DFlash2 TP1 163.7/1128/2826、DSpark TP2 171.5/1082/2402、DFlash2 TP2 251.6/1626/3524，即 TP2 的相对优势随并发上升而收窄（C1 +54%、C4 +44%、C16 +25%），作者据此建议交互/Agent 场景用 TP2、纯高吞吐批处理用 TP1 [S6]。

该实录最有价值的部分是对 SM120 生态限制的明确指认：RTX PRO 6000 与 RTX 50 系为 SM120，而 B100/B200/GB200 为 SM100，预编译的 FP8 算子栈不可互换；FlashInfer 预编译 cubin 只发布 SM100（SM120 需源码 JIT），trtllm_mha 仅支持 SM100，FlashInfer 需要 CUDA ≥ 12.9 才能面向 SM12.x [S6]。它同时记录了九个部署坑点及其根因，包括 FlashInfer 的 get_cuda_version() 回落到 CUDA 12.8 导致编译目标为空（需 CUDA_HOME 指向 13.2）、ninja 不在 PATH、PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True 在 TP2 下破坏自定义 allreduce 的 IPC 注册从而让 CUDA 图捕获失败（作者称这是最反直觉的失败）、DFlash2 需要 master 分支且候选选择器仅在 8 月 19 日合入、flashinfer 与 flashinfer-cubin 版本不一致、cuDNN 版本白名单、企业代理剥离 HEAD 响应 Content-Length 导致 huggingface_hub 的 FileMetadataError、SELinux Enforcing 阻止 /data 下 venv python 执行、以及后台进程随 shell 退出而死亡 [S6]。最终它以用户级 systemd 单元运行（Restart=on-failure、RestartSec=5、TimeoutStopSec=30、双路日志），SIGKILL 测试后约 45 秒恢复 API 200 且 C1 仍有 276 token/s；服务以 max_running_requests=48 为上限，瓶颈是 GDN 状态槽而非 KV [S6]。作者还强调投机解码吞吐对提示词领域高度敏感（代码/数学接受率最高，创意长文最低），表中数字均为代码提示、256 token 输出的有利情形，同样配置在通用提示下 C16 仅约 805 token/s 而非 1929 token/s；57K 上下文时 DSpark TP1 退化到 3.8 token/s，而 DFlash2 TP2 仍有 9.4 token/s [S6]。这些限定条件对本案例（代码 Agent + 文档问答混合负载）尤其重要：不能直接引用最优点数字。

六、把需求映射到两套方案的现状判断。按委托方提供的数据，方案 A 的权重显存约 510GB；昇腾 910B 单卡存在 32GB 与 64GB 两种规格 [S5]，若一体机为 8×64GB 则总显存约 512GB，权重几乎占满，KV 与激活几无余量，这意味着要么需要更多卡、要么依赖其 CSA2 压缩 KV 的实际压缩比。这是基于算术的推断，不是任何材料记载的结论，且 CSA2 的压缩比与 128K 上下文下的真实占用在本次材料中无任何数据，属于必须由厂商以实测回答的空白。方案 B 的 4×96GB 合计 384GB，320B 总参在 FP8 下约 320GB 量级、在 INT4 下约 160GB 量级，前者余量约 64GB、后者余量过半；两者都属可行的容量区间，但 FP8 情形下的 KV 预算偏紧，尤其面对 128K 峰值上下文。吞吐方面可做一个极粗略的推算：以 [S3] 中“每 token 约 5B 激活的 MoE 在单卡上单流 185 token/s”为锚点，按激活参数近似反比外推，18B 激活的模型单卡单流约在数十 token/s 量级，明显高于 25 token/s 的单路门槛；而 10–15 路并发乘以 25 token/s 仅需 250–375 token/s 聚合，相对 [S3] 的单卡 1786 token/s@64 与 [S6] 的 3524 token/s@C16 都存在数量级余量。结论是：本案例的约束瓶颈大概率不在聚合算力，而在长上下文下的显存与 KV 容量、首 token 延迟与工程可维护性。该推算忽略了访存带宽差异、MoE 路由分布、KV 读取放大与精度格式差异，只能用于排除“算力绝对不足”这一种假设。

## P3 · 挑战

一、算子与框架适配的坑点，两条路线性质不同。昇腾侧的适配风险集中在“环境—算子—图模式”三段链条。第一段是环境继承：同一模型在原生 vLLM 下可用、在 Xinference 下报 dtype 错，根因是自定义 GDN/Mamba 算子路径未继承、回退到 CANN 内置算子后被拒绝，处置方式是核对 ASCEND_CUSTOM_OPP_PATH 与 LD_LIBRARY_PATH 并统一 source 环境 [S1]。这意味着任何“加一层封装”的动作（无论是推理框架、网关还是容器化改造）都可能破坏算子可见性，而本案例的运维只有一名兼职人员，此类隐式依赖是长期负担。第二段是算子覆盖与回退：迁移教程明确要求逐个确认算子而非依赖 transfer_to_npu 的自动映射，并以 logit 差异 1e-2/1e-1 作为正常与异常的分界 [S5]；FAQ 亦指出设备支持取决于 TorchNPU 支持情况，否则需要自定义算子 [S4]。第三段是图模式约束，这一条与本案例高度相关：FAQ 记载 DeepSeek 系列在 NPU 图模式下，MLA 加图模式要求每个 KV head 对应 32、64 或 128 个 query head，DeepSeek-V2-Lite 因 16 个注意力头、每 KV 16 query 而落在支持范围外，需等待后续支持；对 DeepSeek-V3 或 R1，应确保张量并行切分后 num_heads/num_kv_heads 落在 {32,64,128} 内 [S4]。委托方所述的 DeepSeek-V4.1-Flash-1017 采用 CSA2 压缩 KV，其注意力是否属 MLA 家族、在目标 TP 度数下每 KV head 的 query 数是否落在该集合内，本次材料无法回答，这是一个必须在 PoC 中首先验证的硬约束：若不满足，可能只能退回 eager 或关闭图模式，而 [S2] 的经验是 enforce_eager=False 才能启用 aclnn 算子，二者方向相反，会直接冲击吞吐。此外 FAQ 还列出了 ACL 图捕获因流资源耗尽而失败时的多条缓解路径（升级 HDK/CANN、缩小 capture size、改用 FULL 或 FULL_DECODE_ONLY、手工设定 PIECEWISE 捕获尺寸、临时关闭图模式），并说明根因是捕获图所需运行时资源超出当前软硬件栈能力，PIECEWISE 还会随模型深度放大 [S4]；对 552B 级别的深模型，这条风险不可忽略。

Blackwell 侧的适配风险则集中在“编译目标与算子包代际”。RTX PRO 6000 属 SM120，与 SM100 的预编译 FP8 栈不通用，FlashInfer 预编译 cubin 仅发布 SM100、SM120 需源码 JIT，trtllm_mha 仅 SM100，FlashInfer 需 CUDA ≥ 12.9 才能面向 SM12.x [S6]。由此衍生的是版本矩阵问题：flashinfer 与 flashinfer-cubin 版本不一致需临时关闭版本检查、cuDNN 白名单需绕过、某些特性只在 master 分支存在 [S6]。多卡方面，[S3] 记录了在 300W、无 NVLink 的双卡机上，vLLM 张量并行在不关闭 P2P 时 NCCL 初始化挂起、关闭后 FlashInfer 预热不可行（100% 利用率但仅 97W、持续十余分钟）；[S6] 则在 8 卡机上用 TP2（同 NUMA、PCIe Gen5 x16 PIX）跑通并拿到收益，但同时记录了 expandable_segments 破坏自定义 allreduce IPC 注册、导致 TP2 下 CUDA 图捕获失败这一最反直觉的坑。把这两条并置可以得出一个有条件的判断：RTX PRO 6000 的多卡并行是“能跑通但强依赖具体版本组合与开关组合”的状态，方案 B 若采用 TP4，风险高于 [S6] 已验证的 TP2，需要预留“TP2×2 副本”或层切分作为退路；层切分在 [S3] 中确实可用（gemma4-31b Q4_K_M 双卡 64.9 token/s、nemotron-120b Q4_K_M 双卡 120.6 token/s）[S3]。最后是模型结构侧的未知数：GLM-5.3-Flash 由 34 层 KDA 线性注意力与 11 层 DSA 稀疏 MLA 组成，而 [S6] 的经验表明线性注意力层在推理引擎中是以“状态槽”而非 KV 计费的，其数量直接决定并发上限（该案例 max_running_requests=48 就是被 GDN 状态槽卡住），并需要一整套 --mamba-* 类参数调优（状态槽从 153.9MB 降到 78.4MB、full-memory-ratio、radix-cache-strategy 等）[S6]。KDA 与 GDN 并非同一算子，vLLM 或 SGLang 对 KDA 与 DSA 的支持成熟度在本次材料中完全空白，这是方案 B 最大的技术不确定性，而非 GPU 本身。

二、吞吐与延迟。首 token 延迟方面，本案例平均输入 32K、峰值 128K，预填充长度是 TTFT 的主导项。方案 B 的正面证据是 [S6] 在 27B 模型、2K 提示下 TTFT 约 60–62ms，且归因于线性注意力的 O(n) 预填充；但该数据是 2K 提示、8 卡机、含投机解码的有利条件，不能线性外推到 32K 输入与 320B 总参模型。方案 A 的正面证据是 [S2] 声称预热脚本可将首请求延迟从 12.3 秒降到 1.7 秒——这个 12.3 秒的冷启动数字恰恰说明“首 token ≤5 秒”这条 SLA 在昇腾侧可能与预热策略强耦合，而该文数据本身不可作为基准（见前节限定）。更结构性的证据来自 FAQ：并发增加 4 倍时 TPOT 上升 0.5–1ms 属正常，但若出现 10–100ms 的剧烈上升，通常源于 KV cache 触顶后的抢占（preemption），日志会显示 KV cache 使用率 99%、KV cache 约 66340 token、16384 token/请求下最大并发约 4.05，缓解手段是提高 gpu-memory-utilization 或降低 max-num-seqs 与 max-num-batched-tokens，且抢占无法完全避免 [S4]。这组数字对本案例有直接警示：在 32K 平均上下文的负载下，KV 容量对并发的限制会先于算力出现，而“抢占导致 TPOT 抖动”会直接违背“单路不低于 25 token/s”的稳定性要求——注意 SLA 是对每路速度的要求，抢占造成的尾部长尾比平均吞吐更致命。长上下文退化亦有实证：[S6] 中 57K 上下文时 DSpark TP1 退化到 3.8 token/s、仅输出 29 个 token，DFlash2 TP2 为 9.4 token/s，8K 单流为 28.6 对 33.7；这说明即使在同一硬件上，长上下文与投机解码策略的组合也可能把速度打到 SLA 之下，而本案例的峰值上下文是 128K。方案 A 的对应风险是 CSA2 压缩 KV 的实际压缩比与 128K 下的表现无任何公开数据。综合而言，两套方案在“10–15 路并发、每路 25 token/s”的聚合吞吐要求上都有余量（推算见前节），真正的风险点集中在首 token 延迟、长上下文尾部长尾与 KV 触顶抢占三处，其中方案 A 的显存余量更紧（510GB 权重对约 512GB 的 8×64GB 配置，属推算），方案 B 的软件栈更生涩。

三、运维成本。人员约束是“一名兼职运维”，这使运维成本的评估维度不是“能不能修”，而是“故障时能否在无人指导下恢复、升级时是否会被版本矩阵卡住”。方案 A 的运维形态是单供应商一体机，理论上责任边界清晰、硬件与镜像同源；但公开材料显示其日常运维需要掌握的知识面并不窄：CANN/torch_npu/vLLM/vLLM-Ascend 四层版本对齐并在故障记录中一并登记 [S1][S5]；环境变量（set_env.sh 两级 source、ASCEND_RT_VISIBLE_DEVICES、PYTORCH_NPU_ALLOC_CONF、TASK_QUEUE_ENABLE）[S5]；容器需 --privileged=true 才能解决 --shm-size 下的 operation not permitted 且带明确安全警告、麒麟系统上 docker pull 可能报 invalid tar header 需离线导入 ARM64 镜像、纯 CPU 机器上源码构建需手工设置 SOC_VERSION [S4]；源码重装可能遇到 C/C++ 编译失败需改用 python setup.py install [S4]；自定义 torch_npu 可能在安装 vllm-ascend 时被覆盖需事后重装指定版本 [S4]。方案 B 的运维形态是自建工作站，优势是通用生态、文档与社区经验丰富、故障可用通用手段定位；代价是 SM120 的源码编译链路、CUDA 双版本共存（系统 12.8 与独立 13.2）、九类环境坑点，以及必须自行搭建进程守护——[S6] 用用户级 systemd 加 linger 实现自动重启，SIGKILL 后约 45 秒恢复，这实际上是把“运维自动化”这件本来应由供应商交付的工作转嫁给了使用方。对只有一名兼职运维的团队，方案 B 的可持续性取决于该人是否具备 Python 环境与 CUDA 编译的调试能力；方案 A 的可持续性取决于供应商响应速度与备件，但一旦需要自行绕过算子或图模式问题，团队几乎无自主能力。此外还有两项常被忽略的成本：电力与散热——910B 满负荷约 310W 的说法出现在不可靠来源 [S2]，RTX PRO 6000 存在 600W 的 Server Edition 与 300W 的 Max-Q 版本，[S6] 使用 600W 版本、[S3] 使用 300W 版本，4 张 600W 卡的 GPU 侧功耗量级约 2.4kW，办公环境部署需评估配电与噪声；以及升级成本——[S4] 显示 vllm-ascend 稳定版通常与同版本 vLLM 对齐、RC 版可能与对应的 vLLM 正式版对齐、主干每个提交都宣称兼容，这意味着跟随上游升级需要持续投入验证，而冻结版本又会在新模型支持上落后。

四、可验证性与采购风险。这是本案例最容易被忽视、却可能决定成败的一项。本次检索的六份材料中没有任何一份提及 DeepSeek-V4.1-Flash-1017 或 GLM-5.3-Flash，也没有任何一份提供昇腾 910B 一体机的价格、交期或 200 万元预算内的配置清单；因此本报告无法就“哪套方案在预算内”给出事实性结论，只能指出该信息缺口并要求以报价单与 PoC 补齐。与此相关的次级风险是模型代号的稳定性——型号后缀形如日期编码（推断，非材料记载），若确为按期发布的迭代版本，则版本更替频率会直接影响运维负担与回归测试成本；委托方回答称两个模型均为 2026 年 8 至 10 月最新开源，这一时间线与材料中 2026 年 8 月至 10 月的实测记录在时间上相容，但不能作为型号存在的证据。第三项风险是基准不可比：[S3] 与 [S6] 的吞吐数字分别来自不同模型、不同并发口径（512 token 与 256 token 输出）、不同功耗墙（300W 与 600W）与是否启用投机解码，[S6] 明确说明其表格是最有利的代码提示情形、通用提示下 C16 仅约 805 而非 1929 token/s，且与社区 wiki 的 141/120.8 token/s 等条目因卡型与草案不同而不可直接比较；[S2] 的数字则存在内部不自洽。因此任何“看别人跑分选型”的做法在本案例中都不成立，必须以自身负载（32K 平均输入、RAG 片段拼接、代码 Agent 多轮工具调用、高前缀缓存命中）自建基准。

## P4 · 展望

一、基于现有证据的倾向性判断。需要再次强调，以下为基于材料的推断与建议，不是已验证的结论。第一，在容量维度上，方案 B 的算术安全边际更清楚：320B 总参在 4×96GB（合计 384GB）上以 FP8 部署约占用 320GB 量级、以 INT4 部署约 160GB 量级，前者尚余约 64GB 供 KV 与激活、后者余量过半；而方案 A 按委托方给出的约 510GB 权重，与典型 8×64GB 一体机的约 512GB 总显存几乎抵满，KV 与 128K 峰值上下文的空间取决于 CSA2 压缩的实际效果，而该效果无公开数据（推算，非材料记载）。第二，在软件成熟度维度上，两条路线都有明确的“坑”，但性质不同：昇腾侧的坑多为环境继承与图模式约束，属于“一旦打通则相对稳定、但打通依赖厂商”的类型 [S1][S4]；Blackwell SM120 侧的坑多为编译目标与版本组合，属于“社区在快速追赶、当前需自行排障”的类型 [S6][S3]。第三，在组织匹配维度上，仅有的一名兼职运维不太可能同时承担 CUDA 源码编译调试与 CANN 版本矩阵维护，因此无论选哪条路线，都应把“供应商/集成商承担软件栈责任”作为合同条款，而不是默认由内部消化。若必须在不做 PoC 的前提下排序，则“无信创硬约束 + 优先易维护 + 显存余量”这三条需求共同指向方案 B 作为主选、方案 A 作为备选；但这一倾向的置信度受制于 KDA/DSA 在主流推理引擎中的支持成熟度这一完全空白的变量，因此不构成最终建议。

二、必须执行的 PoC 与验收口径。建议在签约前用两到四周做一次面向自身负载的对照验证，并把验收标准写成可测条款。需要测的项包括：(1) 32K 输入下的 TTFT 分布（P50/P95/P99），门槛 5 秒，并记录冷启动与预热后的差异——[S2] 声称预热可把首请求从 12.3 秒降至 1.7 秒，无论该数字是否可信，冷启动必须单独测试；(2) 10 路与 15 路并发下的每路生成速度分布，门槛 25 token/s，重点看尾部而非均值，因为 [S4] 明确指出 KV 触顶引发的抢占会造成 TPOT 剧烈上升且无法完全避免，此时均值达标而尾部不达标是常见失败形态；(3) 128K 峰值上下文下的单路可用性与 KV 占用，[S6] 的 57K 上下文退化案例（DSpark TP1 降至 3.8 token/s）说明这一项不能省略；(4) 前缀缓存命中率对 TTFT 的实际改善，本案例代码 Agent 高命中，应单独构造多轮工具调用会话测量；(5) 稳定性与恢复：连续 72 小时压测、进程被杀后的自动恢复时间（[S6] 的 systemd 方案约 45 秒可作参照）、以及显存是否存在缓慢增长（[S2] 提到的内存泄漏检查方法可作流程参考，但其数字不可采信）；(6) 精度回归：以 [S5] 提出的 logit 差异 1e-2/1e-1 分界作为筛查线，对代码补全与 RAG 问答各建一组固定用例。

三、针对两套方案的具体缓释措施。若选方案 A，应在合同中明确：实际交付卡型与 vLLM-Ascend 支持矩阵逐条对应（注意 910B 对应 Atlas A2 内核包受支持，而 FAQ 将“Ascend 910/910 Pro B”列为不支持且无计划 [S4]）；厂商须以书面实测回答“在目标 TP 度数下 MLA 图模式的每 KV head query 数是否落在 32/64/128 集合内”[S4]；须提供 128K 上下文下的 KV 实测占用与最大并发数；须承诺软件栈升级由厂商负责并在升级后重跑验收用例；运维方需保留 ASCEND_CUSTOM_OPP_PATH、LD_LIBRARY_PATH 与 CANN/torch-npu/vLLM/vLLM-Ascend 版本的登记制度 [S1][S5]。若选方案 B，应采取：采用 TP2×2 副本或层切分作为默认拓扑而非直接上 TP4，因 [S6] 只验证了 TP2、[S3] 在双卡机上记录了 vLLM TP 的 NCCL 与 FlashInfer 预热失败；固定一套已验证的版本组合（驱动、CUDA、推理引擎、flashinfer/cubin）并禁止随意升级，因为 [S6] 的多数坑点都源于版本错配；用用户级 systemd 加 linger 实现守护与自动重启 [S6]；明确 96GB 卡是 300W Max-Q 还是 600W Server Edition，前者功耗友好但需接受性能差异 [S3][S6]；对 GLM-5.3-Flash 的 KDA/DSA 支持情况要求集成商出具可复现的部署脚本与压测报告，这是本方案唯一无法从现有材料推断的部分。

四、演进趋势与需要持续监控的变量。从材料可见四个方向。其一是线性注意力与稀疏注意力的混合结构正在成为长上下文模型的主流形态：[S6] 的 27B 模型采用 48 层 GDN + 16 层 GQA，委托方所述的 GLM-5.3-Flash 采用 34 层 KDA + 11 层 DSA，其共同效果是预填充近似 O(n)（[S6] 观测到 2K 提示 TTFT 约 60–62ms）并把并发的瓶颈从 KV 转移到“状态槽”，这会改变容量规划的方法论——未来并发上限可能由状态槽数量而非 KV 字节数决定 [S6]，但同时也要求推理引擎为新算子持续投入适配。其二是投机解码成为单流性能的主要来源：[S6] 从 46.6 提升到 251.6 token/s 的 5.4 倍收益中，投机采样贡献了主要部分，且收益高度依赖提示词领域（代码/数学接受率最高），这对本案例的代码 Agent 场景是利好，对文档问答则需打折看待；同时 57K 长上下文下投机策略会退化，说明该收益并不稳健。其三是 KV 量化与压缩：昇腾侧有 CSA2 压缩 KV 的设计，Blackwell 侧有 fp8_e4m3 KV 使每 token 占用从 65.5KB 降至 32.8KB 的实测 [S6]，两者都在缓解长上下文成本，但都需要在 128K 峰值下实测验证。其四是软件栈的收敛速度：vLLM-Ascend 已具备 P-D 分离（Mooncake）、w8a8/w4a8/w4a4 量化与较完整的测试体系，并规划了逐 PR 的性能站点与发布版性能/精度报告 [S4]；Blackwell SM120 侧则依赖上游把预编译 cubin 从 SM100 扩展到 SM12.x [S6]。这两条曲线谁先收敛，会实质改变两套方案的运维成本对比，建议在选型后保持每季度一次的复评。

五、结论性建议与剩余空白。以 200 万元预算、10–15 路峰值并发、32K 平均 / 128K 峰值上下文、5 秒 TTFT、25 token/s 单路、一名兼职运维为约束，本报告的建议是：把方案 B（4× RTX PRO 6000 跑 GLM-5.3-Flash）作为默认推进方向，但把“KDA/DSA 在所选推理引擎中的可运行性与 128K 下的 KV 实测”设为 Go/No-Go 门槛；把方案 A（昇腾 910B 一体机跑 DeepSeek-V4.1-Flash-1017）作为备选，且仅在厂商能以书面实测证明“510GB 权重可在预算内配置中容纳 128K 上下文与 10–15 路并发”“MLA 图模式约束在目标 TP 下满足”“升级由厂商负责”三项条件时才转为优选。剩余的明确信息空白有三处，须由采购流程补齐而非由分析填补：一是两个模型的公开可核验规格（本次六份材料均未提及，全部规格来自委托方回答）；二是两套方案在 200 万元预算内的实际报价、交期与保修条款（材料中无任何价格信息）；三是 GLM-5.3-Flash 的 KDA/DSA 与 DeepSeek-V4.1-Flash-1017 的 CSA2 在各自目标推理引擎中的支持状态（材料中无任何记载）。在这三处空白被填补之前，本报告的定量结论都只应被视为区间估算与风险排序，而非可签署的技术承诺。
